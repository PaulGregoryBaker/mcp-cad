The full `npx vitest run` integration suite is independently flaky/non-deterministic,
unrelated to this refactor:
  - Built the pre-refactor addon from commit 70ea213 (parent of the refactor commit) in an
    isolated git worktree and swapped it into ts/geometry_addon.node for an A/B comparison.
  - Full unfiltered suite with the OLD (pre-refactor) addon crashed with SIGSEGV on 2/2 runs,
    at the IDENTICAL point both times (right after
    semantic_mapping.integration.test.ts "resolveAtRevision ... REVISION_NOT_FOUND").
    This proves the segfault is a pre-existing native-layer issue, not introduced by the split.
  - Full unfiltered suite with the NEW (refactored) addon completed cleanly on 2/2 runs (no
    crash), but the exact set of failing tests varied between runs (25 failed/566 passed vs.
    22 failed/569 passed) — confirming the integration suite has inherent run-to-run flakiness
    (shared native g_service singleton state across a long sequential singleFork run),
    independent of which addon binary is loaded.
  - The deterministic Catch2 C++ suite (geometry_tests, not flaky) was already verified
    byte-identical pre/post refactor in an earlier pass: 54 cases, 50 passed, 1 failed,
    3 skipped; 700 assertions, 699 passed, 1 failed — same single pre-existing failure on
    both builds.
  - New TS integration test files added since the Jun 9 baseline capture (booleans,
    direct_edits, fuse_y_contact, merge_asymmetric_flat, merge_tab_bracket,
    merge_unfold_dxf_content, fuse_preflight.unit) were confirmed to already exist (via
    `git cat-file -e`) at pre-refactor commit 70ea213, so their failures predate this refactor
    and are not new regressions.

Conclusion: no deterministic regression attributable to the service-decomposition refactor
was found. Do not use ad-hoc `vitest run <file> <file> ...` CLI invocations to compare
results — vitest's "projects" config requires the integration project's
`pool:'forks'/singleFork:true` grouping for native-state isolation; passing explicit file
args from multiple projects bypasses that and produces spurious GE_SOLID_NOT_FOUND /
GE_SHELL_NOT_FOUND noise plus a much more reliable SIGSEGV trigger. Always use the
unfiltered `npx vitest run` (or `--project=<name>`) for any future regression comparison.
