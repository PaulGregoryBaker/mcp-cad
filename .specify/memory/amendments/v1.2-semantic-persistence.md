# Constitution Amendment v1.2 — Semantic Persistence (Dolt)

**Status**: Proposed

**Filed**: 2026-05-21

**Targets**: Constitution v1.1 → v1.2

**Affected resolution**: `D3` (State persistence) in the Constitution's "Technology Stack
& Architectural Decisions" table, sourced from [Engineering-Design.md §1](../../Engineering-Design.md)

---

## 1. Summary

The Constitution currently resolves state persistence as
`D3-A: In-memory, session-scoped only`. This amendment introduces a second, **bounded**
resolution `D3-B` covering only the semantic graph and transaction metadata for the
Semantic CAD MCP feature (see [SemanticCad/MVP.md](../../SemanticCad/MVP.md) Phase 1).

Geometry state — BREP shapes, tessellations, the OCCT in-memory model — **stays in
memory + file-backed**, exactly as today. Only the new Semantic Mapping Layer's data
(semantic entities, relationships, bindings, transaction metadata, shape history) moves
to a session-spanning Dolt database.

---

## 2. Rationale

The Semantic CAD MCP's load-bearing claim is that semantic identifiers
(`semantic://braai/firebox_panel_left` and friends) survive topology mutation
across sessions, processes, and product revisions. Per
[SemanticCad/Persistence-Dolt.md §1](../../SemanticCad/Persistence-Dolt.md), Dolt's
branch / merge / `AS OF` primitives collapse the transactional preview/commit/rollback
machinery and semantic lineage queries into native SQL operations, with no custom
infrastructure to invent and maintain.

The current `D3-A` resolution forbids any out-of-process persistence, including for the
semantic store. Adopting Dolt without amending the Constitution would create an undeclared
exception. Amending it preserves the principle of explicit, reviewed architectural
decisions.

---

## 3. Scope of Change

### 3.1 What this amendment does

* Adds `D3-B: In-memory + Dolt-persisted semantic graph (MVP Phase 1 of Semantic CAD)`
  to the resolved tech-stack table.
* Marks `D3-A` as remaining **in force** for geometry state, tessellations, and OCC
  in-memory data.
* Defines a sharp boundary: Dolt stores references to geometry (file paths + content
  hashes); BREP/STEP files store the geometry bytes themselves. The full table
  appears at [Persistence-Dolt.md §3](../../SemanticCad/Persistence-Dolt.md).
* Bumps the Constitution version to **1.2**.
* Adds a changelog entry to the Constitution.

### 3.2 What this amendment does NOT do

* Does **not** alter Principle I (Deterministic Geometry Intelligence). Semantic
  operations remain deterministic — given the same OCCT shape history and the same
  semantic store state, every commit produces the same new bindings.
* Does **not** alter Principle II (Bounded Context Separation). Dolt sits behind a new
  **Semantic Persistence port** owned by a new **Semantic Mapping** context. No OCCT
  primitives leak across the port; no manufacturing rules leak into the semantic store.
* Does **not** alter Principle III (Safety Filter Enforcement). The `fire_rated` check
  and other safety filters are not relocated.
* Does **not** alter Principle IV (Rollback-First). The transaction primitive
  established in [specs/004-transaction-primitive/](../../specs/004-transaction-primitive/)
  is the rollback substrate; Dolt branches simply mirror its lifecycle.
* Does **not** alter Principle V (Kerf Compensation).
* Does **not** alter Principle VI (Structured Errors). The new persistence layer raises
  errors through the same structured-error contract.
* Does **not** alter Principle VII (MVP Scope Discipline). Dolt remains single-session,
  single-writer, local-only. Multi-session and cloud deployment stay deferred.
* Does **not** alter Principle VIII (Configuration Over Hard-Coding). Dolt connection
  parameters (host, port, database, data directory) are added to the existing YAML
  config schema — no hard-coding.
* Does **not** alter Principle IX (Async Export Contract).
* Does **not** introduce auth, multi-tenancy, or remote storage. Dolt runs locally as
  a sidecar process (or embedded), bound to localhost.

## 4. Architectural Impact

### 4.1 New bounded context

A fifth context is added to the four enumerated under Principle II:

| Context                       | Owner                                                                     |
| ----------------------------- | ------------------------------------------------------------------------- |
| Geometry Engine               | (existing)                                                                |
| Manufacturing Domain          | (existing)                                                                |
| Anti-Corruption Layer (FX)    | (existing)                                                                |
| MCP Protocol Layer            | (existing)                                                                |
| **Semantic Mapping (new)**    | TS module that owns the Semantic Store (Dolt) and the Mapping Layer remap |

The Semantic Mapping context speaks to:
- the Geometry Engine via `ShapeHistoryRecord` (read-only, defined in
  [specs/004-transaction-primitive/](../../specs/004-transaction-primitive/));
- Dolt via the **Semantic Persistence port** (new, defined in
  [Persistence-Dolt.md](../../SemanticCad/Persistence-Dolt.md));
- the MCP Protocol Layer via new tools listed in [SemanticCad/MVP.md §3.1](../../SemanticCad/MVP.md).

The Geometry Engine remains ignorant of semantic identifiers, Dolt, and any
manufacturing semantics — preserving Principle II.

### 4.2 Updated tech-stack table

Constitution v1.2 will replace the single `State persistence` row with:

```
| State persistence (geometry)   | In-memory + file-backed BREP, session-scoped (D3-A)              |
| State persistence (semantic)   | In-memory + Dolt-persisted, session-spanning (D3-B, Phase 1 only)|
```

### 4.3 Variant lock

`D3-B` resolves the Dolt variant as **Dolt-MySQL** (MySQL wire protocol) per
[Persistence-Dolt.md §2](../../SemanticCad/Persistence-Dolt.md).
DoltgreSQL (Postgres wire) is explicitly deferred; switching is a future, scoped
decision that does not require a new amendment.

## 5. Migration Plan

This amendment must be ratified **before** Phase 1 work
(`005-semantic-mapping-layer`) begins. No in-flight work is invalidated:

* `004-transaction-primitive` is independent of persistence — it stores
  transactions in TS-side memory. It can ship before this amendment is ratified
  and remains correct under both `D3-A` and `D3-B`.
* The existing sheet-metal MVP (`docs/MVP_SCOPE.md`) does not depend on the
  semantic store and is unaffected.
* Existing integration tests run unchanged. New tests for the Semantic Mapping
  Layer require a running Dolt instance; CI configuration update is part of
  Phase 1 task list.

### 5.1 Required interface-contract updates

Constitution §Governance requires "(2) updating affected interface contracts in
`Engineering-Design.md`." For this amendment, the affected sections are:

* `Engineering-Design.md §1 D3` — add `D3-B` option, mark `D3-A` as still
  in force for geometry.
* `Engineering-Design.md §2 Context Map` — add the Semantic Mapping context with
  ports `ShapeHistoryPort` (Geometry Engine → Semantic Mapping, read-only) and
  `SemanticPersistencePort` (Semantic Mapping → Dolt).

Both updates are tracked as tasks in
[specs/005-semantic-mapping-layer/tasks.md](../../specs/005-semantic-mapping-layer/tasks.md)
and complete before Phase 1 implementation work merges.

### 5.2 Rollout sequence

1. Amendment filed (this document). ✓
2. Constitution edited to v1.2 — tech-stack table + changelog. ✓ (this PR)
3. Engineering-Design.md updated per §5.1. (tracked in `005` tasks T001–T002)
4. `005-semantic-mapping-layer` work begins. (after step 3 merges)
5. `004-transaction-primitive` and `005-semantic-mapping-layer` are independent
   tracks; either may merge first.

### 5.3 Reversibility

The amendment is reversible: if a future review concludes Dolt is the wrong choice,
`D3-B` can be replaced by another resolution (SQLite, embedded Dolt, etc.) without
revisiting the surrounding principles. Reversal would require a new amendment
(`v1.3-*`) per §Governance. The semantic schema in
[Persistence-Dolt.md §4](../../SemanticCad/Persistence-Dolt.md) is portable across any
SQL store; only the branching-and-`AS OF` queries are Dolt-specific and would need
re-implementation.

## 6. Risks

| Risk                                                                       | Mitigation                                                                                   |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Dolt write performance worse than vanilla MySQL                            | MVP write volume is 10²–10³ rows/transaction; verified well within budget in §6.3 of Persistence-Dolt.md. Batch inserts where larger volumes appear. |
| Dolt-MySQL JSON `MEMBER OF` syntax variation                               | Fallback to application-side join documented in [Persistence-Dolt.md §5.4](../../SemanticCad/Persistence-Dolt.md). |
| Operator burden of running `dolt sql-server` alongside the MCP server      | Docker image bundles Dolt; local launcher script wraps both. Docs updated in Phase 1.        |
| Schema migration tooling (none today)                                      | Acceptable for the single Phase 1 schema. A schema-version table + forward-only migration runner is the first task of Phase 2 work. |
| Constitution drift between code and constitution.md if amendment slips     | Phase 1 tasks block until amendment is ratified (T001 of 005 is "verify constitution v1.2 in main"). |
